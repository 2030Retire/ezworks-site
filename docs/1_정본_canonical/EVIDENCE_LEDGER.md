## 0. 배치 원칙 — 프로젝트가 아니라 "문제 모양"으로

구매자는 우리가 도장 플랫폼을 만들었는지 관심이 없다.
그들이 궁금한 건 **"내 승인이 채팅에서 끝나는 문제, 이거 해결됩니까?"** 다.

⛔ 프로젝트별 나열 금지. ✅ **문제 모양별로 묶고, 각 행에 증거 등급을 붙인다.**

### 증거 등급 (이게 정직함의 장치다)

| 등급 | 의미 | 표기 방식 |
|---|---|---|
| **●** | 직접 구축하고 운영 중 / 인도 완료 | 우리 제품·프로젝트로 서술 가능 |
| **◐** | **대규모 조직에서 수행 (익명)** | 역량으로만 서술. ⛔ 회사명·제품명·업종·숫자 금지 |
| **○** | 만들었으나 미출시 | "완성했으나 아직 열지 않음"으로 정직하게 |

> ⭐ 등급을 명시하면 **아무것도 부풀리지 않으면서 재료를 전부 쓸 수 있다.**

## 1. ⛔ 절대 규칙 — 고용주 업무의 취급

대동USA / 카이오티 관련 업무(대시보드·워런티 자동승인·주문 자동승인·ITO 추적·SSO 포털)는
**고용주 업무**다. 통상 업무상 저작물은 회사 소유다.

| | |
|---|---|
| ⛔ **실적으로 쓰지 않는다** | Proof/Evidence = "우리가 만들어 넘긴 것" = 소유권 주장. **여기 넣지 않는다** |
| ✅ **역량으로만 쓴다** | Services = "우리가 풀 수 있는 문제의 종류". 소유권 주장이 아니다 |
| ⛔ 업종 언급 금지 | "농기계", "제조사", "딜러 네트워크" 단어 하나면 익명성이 즉시 무너진다 |
| ⛔ 성과 숫자 금지 | 처리 건수·절감 시간·절감액 — 전부 고용주 데이터. 이력서엔 쓰되 사이트엔 금지 |

같은 원칙이 도장 플랫폼(EZClass) 고객에게도 적용된다 — **"a martial-arts school operator" 수준까지만.**

## 2. 문제 모양 × 결과물

| 고객이 겪는 문제 | 우리가 한 일 | 등급 | 출처 |
|---|---|---|---|
| 승인이 채팅에서 끝나고 **누가 언제 승인했는지 기록이 없다** | 규칙 기반 **자동 승인 + 예외만 사람 큐로**. 대량 청구 심사에 적용 | ◐ | 고용주 업무 |
| 종이·PDF·사진을 **사람이 다시 입력한다** | 문서 OCR → 필드 추출 → 확인만. 모바일 촬영 접수 | ● | EZWorks Expense |
| **본사 시스템이 현지 업무에 안 맞는다** | 다국 ERP 롤아웃에서 프로세스 갭 해소. 7개 법인 동시 런칭 PM | ◐ | 경력 |
| **"이 건 지금 어디까지 갔나"** 에 답이 없다 | 여러 시스템에 걸친 **건별 추적** 화면 | ◐ | 고용주 업무 |
| 내부 도구마다 **로그인이 따로다** | SSO + 역할 기반(RBAC) 단일 포털 | ◐ | 고용주 업무 |
| **수납·청구가 수작업**이고 지점마다 다르다 | 반복 결제 처리 + 다지점 데이터 격리 + 학부모 포털 + 키오스크 체크인 | ● | 다지점 멤버십 플랫폼 |
| 회의·현장 기록이 **남지 않는다** | 음성 → 전사 → 요약 → 노트 파일 자동 생성 | ● | EZHaru (알파) |
| **예산 초과를 사후에 안다** | 신청 시점 예산 조회 · 사전승인 검증 | ◐ | 경력 |
| 회계 입력을 **두 번 한다** | 승인건이 회계로 자동 반영 (QuickBooks 연동) | ● | EZWorks Expense |
| 종이 결재가 **책상에서 멈춘다** | Microsoft 365(Power Apps·Power Automate) 기반 전자결재 + ERP 연동, 모바일 승인 | ◐ | 경력 |

### 다룰 수 있는 시스템 (벤더명 표기 규칙)

| 표기 가능 | 근거 |
|---|---|
| **SAP** (ABAP · MM · SD) | 직접 수행. 롤아웃 PM 2회. **자격 심사 신호** — 이 단어 하나로 "우리 사정을 안다"가 전달된다 |
| **Microsoft 365 / Power Platform** | 직접 구축 (전자결재·예산검증·모바일 접수). SMB에 최고의 제안 — "이미 내고 계신 것 위에 짓습니다" |
| **QuickBooks** | 직접 연동 구현 |
| ERP · 회계 · **CRM** (범주로만) | CRM은 범주로만 열어둔다 |

⛔ **Salesforce는 벤더명으로 쓰지 않는다.** 이력서에 없고, 새 고객사에 처음부터 인도한 적이 없다.
"CRM" 범주로 문만 열어두고, 문의가 오면 대화에서 판단한다.
**사이트에 올릴 조건**: 새 고객사에 한 건을 처음부터 끝까지 인도하면.

⛔ 네트워크·방화벽·VPN·서버 운영은 **서비스 카드로 만들지 않는다.**
사람은 목록에 있는 걸 주문한다 → "PC 안 켜져요" 전화가 온다.
단 **About에 한 줄**: "미국 법인의 IT를 직접 운영해봤기 때문에, 시스템이 들어갈 환경을 압니다."

## 3. 속도 축 — AI가 실제로 바꾼 것

문제 모양이 아니라 **AI가 바꾼 것 자체**라서 별도로 둔다.

| 항목 | 값 | 상태 |
|---|---|---|
| 모바일 앱 — 설계 착수 → 스토어 테스트 배포 | **6일** | ✅ 실측 확인 |
| 다지점 멤버십 플랫폼 — 착수 → 첫 지점 운영 | `[SAMPLE] 10주` | ⬜ 실값 확인 |
| 경비·승인 플랫폼 — 착수 → 기능 완성 | `[SAMPLE] 12주` | ⬜ 실값 확인 |
| 통상 외주 견적 대비 | `[SAMPLE] 기간 1/4, 비용 1/5` | ⬜ 실값 확인 |

> ⛔ **`[SAMPLE]`은 구조 검토용 자리표시다.** 2026-08-20 Hoon 지시로 삽입.
> 확인 전까지 사이트·제안서에 나가지 않는다. 확정 시 표기를 지우고 실측값으로 대체한다.
> ⛔ 숫자를 지어내지 않는다.
> 정확도보다 **자릿수**가 중요하다 — "6개월 → 6주" 급의 대비가 목적.

### 서술 규칙
- "AI 스타트업"으로 자칭하지 않는다. **전달 속도라는 사실로만** 표현한다
- ⛔ "6일 만에 앱" 옆에 대형 시스템 얘기를 나란히 두지 않는다.
  스타트업 속도와 엔터프라이즈 규모를 동시에 주장하면 둘 다 안 믿긴다.
  **속도는 제품 쪽, 규모는 서비스 쪽으로 분리.**
