사례 02

경비·승인 — 기록 없는 승인

경비 · 인보이스 · 승인 · 회계 연계 작업 기록 26일 2026-03 ~ 07

경비 처리가 느린 원인이 사람 수인가. 같은 숫자를 두 번 입력하고 있는지, 그리고 누가 언제 승인했는지가 남는지를 보면 알 수 있습니다.

문제

영수증은 메일로 오고, 같은 숫자를 메일 → 엑셀 → 회계로 옮겨 적습니다. 승인은 구두와 메일로 이뤄져 기록이 남지 않습니다.

해결

수집에서 회계 전기까지 아홉 단계로 고정. 검증에서 걸린 예외가 남아 있으면 승인으로 넘어가지 못하게 게이트를 승인 앞에 두었습니다.

효과

재입력 구간 제거. 승인이 기록으로 남는 행위로 바뀝니다. 인보이스·납품서 2단계 대조로 금액은 맞고 물량이 틀린 건을 잡습니다.

Situation

승인의 부재가 아닌 기록의 부재

영수증은 메일 첨부로 도착하고, 누군가 나중에 스프레드시트에 옮겨 적습니다. 승인은 대화로 끝나서 결정은 있는데 누가 언제 승인했는지가 남지 않습니다. 그리고 같은 숫자를 회계 프로그램에 한 번 더 입력합니다.

여러 회사를 한 플랫폼에서 다루면서 서로의 데이터가 섞이지 않아야 하는 조건도 있었습니다.

Mechanism

수집에서 회계까지 아홉 단계

"영수증 처리"를 하나의 덩어리로 두면 매번 논의가 반복됩니다. 단계를 쪼개고 각 단계의 입출력을 문서에 못 박았습니다.

01
수집

모바일 촬영 또는 파일 업로드. 계좌 거래 내역에서 직접 경비로 저장하는 경로도 있습니다.

02
OCR 추출

거래처·일자·금액·세액을 문서에서 읽어냅니다.

03
검토·보정

사람은 타이핑하지 않고 읽어낸 값을 확인합니다.

04
필드 정리

카테고리·금액·통화·설명.

05
환율 정책 적용

외화 건의 환산 기준을 정책으로 고정합니다. 건마다 사람이 정하지 않습니다.

06
차원 태깅

거래처·고객·프로젝트 축으로 태깅해 나중에 축별로 집계할 수 있게 합니다.

07
리포트 생성 · Finalize 검증

제출 직전에 정책 위반을 검사합니다.

08
승인

경비와 인보이스가 같은 승인 요청 구조를 공유합니다. 승인 대상 종류가 늘어도 승인 로직을 다시 만들지 않습니다.

09
회계 연계

승인된 건이 QuickBooks Online으로 넘어갑니다. 거래처·고객·프로젝트 차원도 함께 넘어갑니다.

검증 정책 게이트 — 예외 잔존 시 승인 차단

검증에서 걸린 항목이 남아 있으면 승인 단계로 넘어가지 않습니다. 경고를 띄우고 통과시키는 것과 다릅니다. 승인이 난 건에는 미해결 예외가 없다는 것이 보장됩니다.

인보이스 · 납품서 2단계 대조

납품서·패킹슬립을 수집해 인보이스와 매칭합니다. 매칭이 안 되면 회계 시스템의 발주 정보를 두 번째 대조 소스로 사용합니다.

1차 = 납품서 대조 · 2차 = 발주 정보 대조

Friction

실제로 되돌린 것들

고화질 사진이 메모리를 넘겼습니다. 모바일 촬영 업로드에서 이미지를 리사이즈하려고 통째로 메모리에 올리다 저메모리 오류가 났습니다. 두 가지로 되돌렸습니다 — 작은 파일은 리사이즈를 아예 건너뛰고, 리사이즈가 실패하면 원본을 그대로 올립니다. 업로드 자체가 막히지 않는 쪽을 택했습니다.

썸네일을 누르면 미리보기가 아니라 다운로드가 됐습니다. 파일 응답에 파일명을 지정한 것이 첨부 다운로드를 강제하고 있었습니다. 한 줄 문제였지만 사용 흐름 전체를 어긋나게 하던 종류입니다.

브랜치가 갈라지며 마이그레이션 번호가 충돌했습니다. 두 갈래에서 같은 번호를 점유해, 한쪽에 별도 네임스페이스를 붙여 분리하고 통합 시 병합하도록 남겼습니다.

고화질 모바일 이미지는 여전히 기기별 메모리 한계 차이가 있을 수 있으나, 이번 수정으로 실패 시 전체 업로드가 막히지 않고 원본 fallback으로 진행된다.

완전히 해결했다고 적지 않고, 남은 위험을 그대로 적어 둔 기록입니다.

Now

현재 범위

멀티테넌트 격리, 문서 OCR, 승인 라우팅, 회계 연계가 모두 동작합니다. 어떻게 누구에게 열지를 정하지 않았습니다. 작업 기록이 남은 날은 26일이고 기간은 2026년 3월 말부터 7월 말까지입니다.

사례 03

음성 기록 — 서버 없는 설계

음성 기록 · 전사 · 요약 설계 착수 → 스토어 테스트 6일 Android

회의 기록이 남지 않는 원인이 습관인가. 기록하는 수고가 회의 자체보다 큰지를 보면 알 수 있습니다.

문제

회의는 매일 있는데 기록은 남지 않습니다. 녹음해도 다시 듣는 사람이 없어 기록이 되지 못합니다.

해결

서버를 두지 않는 것이 출발점. 파일은 사용자 소유의 저장소에 남고, 분류를 누르면 폴더가 결정됩니다.

효과

보관 주체가 우리가 아니므로 서비스가 사라져도 파일이 남습니다. 업로드가 확인되기 전에는 원본을 지우지 않습니다.

Mechanism

출발점 — 서버를 두지 않는 것

녹음이 사용자 기기에서 본인 클라우드로 바로 가고, 전사는 사용자가 본인 키로 연결한 AI 서비스에서 돌아갑니다. 중간에 우리 서버가 없습니다. 편의 기능이 아니라 구조로 박아 둔 제약입니다 — 나중에 정책을 바꿔서 데이터를 볼 수 있게 되는 경로 자체가 없습니다.

분류 선택 = 폴더 결정

녹음마다 사용자가 지정한 폴더로 들어갑니다. 업무 회의는 업무 드라이브로, 개인 메모는 개인 드라이브로. 파일명을 붙이거나 옮기는 단계가 없습니다.

업로드 확인 전 삭제 금지

앱이 꺼지거나 연결이 끊겨도 녹음이 남습니다. 저장 실패를 조용히 넘기지 않는 쪽으로 설계했습니다.

노트 형식 — 일반 마크다운

오디오 파일 옆에 텍스트로 저장되므로 파일 탐색기에서 검색되고 다른 편집기에서 열립니다. 앱을 지워도 결과물이 남습니다.

Governance

미검증 사실 위의 코드 금지

녹음 앱은 녹음 동의법이 1번 법역입니다. 지역마다 규정이 다르고, 잘못 판단하면 되돌리기가 비쌉니다.

등급의미코드 착수
[확정]법령 조문·공식 문서로 직접 확인됨가능
[고신뢰]업계 표준 해석. 반대 해석을 찾지 못함조건부
[❓미검증]확인되지 않음금지

모든 법적·정책적 서술에 이 등급을 붙이고, 등급이 없는 서술은 무효로 취급합니다. 미검증 항목은 별도의 사실확인 절차로 넘어가고, 확인되기 전까지 그 위에 기능을 올리지 않습니다.

이 규약이 있는 이유는 규제를 과대평가해도 실패하고 과소평가해도 실패하기 때문입니다. 등급이 있으면 무엇을 모르는지가 목록으로 남습니다.

스코프 정직성

문서 첫 장의 범위 선언 — 「상용 SaaS가 아니다」

개인과 소수 지인용 알파라는 것을 정본에 명시했습니다. 그래서 제약의 무게를 "지금 컴플라이언스"가 아니라 "제품화할 때 아키텍처를 다시 짜게 되는 것을 지금 싸게 막는 것" 기준으로 판정합니다.

지금 필요한 것보다 크게 만들지 않기 위해, 지금 무엇이 아닌지를 먼저 적은 것입니다.

Now

현재 범위

  • Android 비공개 알파. iOS는 계획만 있고 시작하지 않았습니다.
  • 본인 계정 위에서 돌아가기 때문에 최초 설정에 10분 정도 걸립니다. 클라우드 연결과 API 키 입력.
  • 설계 착수부터 스토어 테스트 배포까지 6일. 실측입니다.
  • 여전히 사람이 하는 일 — 전사가 확신하지 못한 구간의 확인, 그리고 용어 교정.

Summary

정리

1승인이 없던 것이 아니라 승인 기록이 없었습니다. 같은 숫자를 여러 번 옮겨 적는 구간도 함께 있었습니다.

2단계를 아홉 개로 고정하고 검증 게이트를 승인 앞에 두었습니다 — 뒤에 두면 되돌리는 일이 생깁니다.

3음성 기록에서는 확인되지 않은 사실 위에 코드를 올리지 못하게 등급 규약을 두었습니다.

다음 한 가지

같은 숫자를 두 번 이상 입력하는 구간이 있는지 한 줄로 알려주시면 됩니다.

두 사례의 메커니즘·기간·마찰은 프로젝트 문서와 작업 로그에서 확인된 사실입니다. 지어낸 수치는 없습니다.
