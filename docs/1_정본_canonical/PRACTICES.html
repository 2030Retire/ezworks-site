운영 규율

자동 판정을 켜는 순서

"AI가 잘못 판단하면 어떻게 되나"가 자동화 도입에서 가장 흔한 질문입니다. 답은 보증이 아니라 순서로 합니다. 아래는 실제 프로젝트에서 쓴 방식이며, 고객사와 업종은 밝히지 않습니다.

「AI가 잘못 판단하면 어떻게 되나」에 보증으로 답할 수는 없습니다. 순서로 답합니다.

문제

자동 판정을 켜는 결정은 되돌리기 비쌉니다. 잘못 승인된 건은 이미 지급되었거나 이미 출하되었습니다. 보증은 사고를 막지 못합니다.

해결

판정 로직을 그대로 두고 실행 권한만 세 단계로 올립니다. 기록만 → 유예 후 확정 → 즉시 확정.

효과

켜는 시점이 합의가 아니라 데이터로 정해집니다. 사람 결정과의 일치, 개입 빈도가 조건입니다.

Rollout

세 단계 — 로직 고정, 권한만 상승

같은 판정 로직을 그대로 두고 실행 권한만 단계적으로 올립니다. 코드를 바꾸지 않고 설정 한 줄로 단계를 옮깁니다.

1 · shadow
판단만 하고 아무것도 실행하지 않습니다

매 사이클마다 판정을 내리고 감사 로그에만 남깁니다. 그 기간 동안 사람의 결정과 시스템의 판정을 나란히 비교합니다. 어긋나는 건이 나오면 규칙을 고칩니다. 실제 업무에는 영향이 없습니다.

2 · staging
예비 승인 큐에 넣고 유예 시간을 둡니다

판정된 건이 바로 확정되지 않고 큐에 들어갑니다. 정해진 영업시간이 지나면 자동 확정되고, 그 사이 사람이 들어와 막을 수 있습니다. 기본값이 통과이면서 개입 여지가 있는 상태입니다.

3 · live
즉시 실행합니다

shadow에서 판정이 사람 결정과 충분히 일치하고, staging에서 개입이 거의 발생하지 않게 된 뒤에 켭니다.

묻는 사람: "잘못 승인하면요?" — 답: "몇 주 동안 판단만 시켜 보고, 사람 결정과 얼마나 맞는지 본 다음에 켭니다."

Rules as Configuration

판정 기준의 위치 — 코드가 아니라 설정

기준이 코드 안에 있으면 숫자 하나 바꿀 때마다 개발자를 불러야 합니다. 그러면 기준은 현실을 못 따라가고, 사람들은 시스템을 우회하기 시작합니다.

바꾸는 것누가개발 필요
임계값·허용 범위업무 담당자 또는 PM없음 — 설정 파일 수정
새로운 종류의 판정 규칙개발자있음 — 규칙 모듈 추가 후 등록

변경에 붙는 유예 시간과 효력일

규칙 변경은 영업시간 기준 최소 유예를 두고 등록되며, 각 변경에 언제부터 적용되는지가 필수 항목입니다. 어제 처리된 건이 오늘 바뀐 기준으로 재평가되지 않게 하기 위한 것입니다.

배포 전 영향 범위 집계

바꾼 기준을 실제 데이터에 실행하지 않고 통과시켜 몇 건이 달라지는지 먼저 확인합니다. 숫자를 보고 나서 배포합니다.

이전 버전으로의 즉시 복귀

설정 파일 교체만으로 롤백됩니다. 긴급 변경 경로도 있지만, 그 경우 감사 로그에 별도로 표시됩니다 — 우회했다는 사실 자체가 기록됩니다.

실패 사유 전량 수집

첫 조건에서 걸리면 멈추는 방식과, 모든 조건을 평가하고 실패 사유를 전부 모으는 방식이 있습니다. 후자를 기본으로 씁니다 — 담당자가 한 번에 전체 사유를 보고 고칠 수 있어야 하기 때문입니다.

Read-only First

첫 연결은 읽기 전용

회사의 핵심 데이터가 들어 있는 시스템에 붙을 때, 처음 연결은 읽기 전용으로 합니다. 대시보드나 조회 화면은 읽기만으로 전부 만들 수 있고, 그 단계에서 데이터 구조와 실제 값의 의미를 확인합니다.

쓰기가 필요해지는 시점에는 이미 그 시스템을 이해한 상태입니다. 그리고 쓰기는 원래 시스템을 고치는 대신 별도 제어 지점을 추가하는 쪽을 먼저 봅니다.

묻는 사람: "우리 시스템 망가지면요?" — 답: "처음에는 읽기 권한만 받습니다."

Better Idea Wins

더 나은 안의 수용

한 프로젝트에서 특정 조건의 주문을 처리 대상에서 제외하는 방식으로 설계를 보내고 검토를 요청했습니다. 담당 팀이 다른 방식을 회신했습니다 — 제외하지 말고 정상적으로 흘려보낸 뒤 다음 단계에서 진행 플래그로 막자는 안이었습니다.

그쪽이 더 나았습니다. 원래 흐름을 건드리지 않고, 제어 지점이 명확하고, 되돌리기도 쉬웠습니다. 아키텍처를 바꿨습니다.

기존 요청 문서는 지우지 않고 보낸 시점의 스냅샷으로 보존하고, 새 문서에 "이것이 현재 정답지이며 앞 문서를 대체한다"고 명시했습니다. 왜 바뀌었는지가 남아야 나중에 같은 논의를 다시 하지 않습니다.

설계를 방어하는 것과 결과를 얻는 것은 다른 일입니다.

Same Discipline

세 제품에 반복된 같은 규율

원칙으로 선언한 것이 아니라, 서로 다른 프로젝트에서 같은 방식으로 결정한 기록입니다.

어디서무엇을 했나
회원·수납 플랫폼청구 규칙이 설계 보증과 충돌하는 것을 발견하고, 화면 단계에서 확정하지 않고 결정 게이트로 올렸다
경비·승인 플랫폼검증에서 걸린 예외가 남아 있으면 승인 단계로 넘기지 않는다
음성 기록 앱확인되지 않은 법적 사실 위에는 코드를 올리지 못하게 등급 규약을 두었다
심사 자동화판정 권한을 세 단계로 나누고, shadow에서 사람 결정과 비교한 뒤에 올린다

네 건 모두 같은 규율입니다 — 확실하지 않으면 진행하지 않는다. 다르게 말하면, 확실하지 않다는 것을 알아차릴 수 있는 장치를 먼저 만들어 둡니다.

서술 범위

이 문서의 방식은 실제 프로젝트에서 사용한 것입니다. 고객사·고용주·업종·제품명과 처리 건수 같은 운영 지표는 포함하지 않습니다. 방법에 대한 서술이며 실적에 대한 주장이 아닙니다.

Summary

정리

1「잘못 판단하면」에 보증으로 답하지 않습니다. 로직을 두고 실행 권한만 세 단계로 올립니다.

2판정 기준은 코드가 아니라 설정에 둡니다. 담당자가 바꾸고, 유예와 효력일이 붙고, 즉시 되돌릴 수 있습니다.

3돌아가는 시스템의 첫 연결은 읽기 전용입니다. 쓰기가 필요해질 때는 이미 그 시스템을 이해한 상태입니다.

다음 한 가지

사람이 매번 같은 기준으로 승인하고 있는 업무가 있는지 한 줄로 알려주시면 됩니다.
